# Распознавание порталов

Распознавание выполняется локально. Сначала определяется название и показывается карта локации, затем — вместимость и время закрытия. Запись портала выполняется после полного результата.

## Размер портала без счётчика людей

С 3 октября 2026 распознаватель публикует только размер портала: знаменатель
`/7` или `/20`. Первое число не нужно для маршрута и не оценивается по заполнению
полосы. В результате `capNum` всегда `null`, `capNumApprox` — `false`; размер
хранится в `capMax`, его подтверждение — в `capMaxKnown`.

Несколько чтений с разными первыми числами могут подтвердить один размер.
Неизвестный числитель или несоответствие заливки не отменяют прочитанный
знаменатель. Конфликт `/7` и `/20` оставляет размер неизвестным. Одиночная цифра
без положения в дроби и строка перезарядки не считаются подтверждением размера.
Если слэш потерян OCR, компактная запись дроби может служить поддержкой;
у полного широкого выреза допускается только явный слэш, чтобы соседний счётчик
перезарядки не голосовал за размер по последним цифрам.

Если обычные вырезы не дают размер, проверяется узкая область дроби в исходных
оттенках серого. При несовпадении масштаба имени с масштабом экрана допускается
повторная обработка вместимости в масштабе экрана, если высота полосы ему
соответствует. Это обработка того же кадра; геометрия для имени и таймера не меняется.

Структурная проверка дроби при восстановлении целой карточки сохранена: она
помогает отличить портал от постороннего интерфейса. Числитель из неё наружу
не передаётся. Экспорт маршрута также показывает только вместимость.

Это изменение чтения вместимости; обнаруженные в разборе сегодняшнего архива
ошибки таймера рассматриваются отдельно. Исторические результаты ниже относятся
к указанным в них прогонам, а не к гарантии качества на новых изображениях.

- Название проверяется по справочнику и ближайшим кандидатам.
- Вместимость читается в отдельной области; точное значение требует согласованных результатов.
- Таймер выделяется по цвету и геометрии текста. Строки закрытия и перезарядки обрабатываются отдельно.
- Спорное короткое время остаётся неподтверждённым.
- Срок закрытия отсчитывается от получения кадра. Очередь и распознавание его не продлевают.
- Масштаб подбирается по кадру и полосе портала. Кэш хранит до 12 профилей обработки.

## Проверка белых таймеров и восстановление карточки

Публичный `recognizeTooltip` дополнительно проверяет полноту белой строки, видимые
цифры и единицы времени. Проверяется и уже полученное число: повторяющееся чтение
обрезанной строки не должно сокращать время портала. При необходимости отдельно
читаются числовые блоки и восстанавливается карточка по имени, полосе и служебным
подписям. Противоречащие друг другу подтверждения оставляют время неизвестным.

Алгоритм находится в `app/lib/portal-recovery/`, модель символов — в
`app/data-static/portal-timer-glyphs.json`. Для работы не нужны исследовательские
скрипты, архивные фотографии, сеть или повторный захват экрана. Используются тот же
OCR-процесс и тот же кадр. Ранний показ имени и чтение вместимости сохраняются.

Повторный OCR одинаковых фрагментов переиспользуется только внутри одной попытки.
Поиск служебных подписей заканчивается после достаточного подтверждения; чтения
имени и дроби вместимости, способные выявить конфликт, выполняются полностью.
Красные таймеры продолжают использовать отдельный проверенный алгоритм.

Ограничение чтения портала остаётся 12 секунд с ограничением каждого OCR-запроса.
При сбое дополнительной проверки приложение сохраняет уже прочитанные имя и
вместимость, а время оставляет неизвестным. Отсчёт закрытия по-прежнему привязан к
моменту захвата, поэтому затраченное на проверку время не продлевает жизнь портала.

В исследовательском контроле v5 на 893 уникальных архивных снимках получены
850 правильных таймеров из 856 читаемых (99,30%), 0 ошибочных принятий и 6 отказов.
37 снимков без надёжно читаемого времени остались без числового ответа. Это результат
на изученном архиве, а не гарантия точности на новых игровых сценах.

При внедрении 3 октября 2026 года этот результат повторён через настоящий публичный
метод приложения на всех 893 снимках дважды: с исключением шаблонов своего эпизода
и со всей моделью, как в обычной работе. Числа, имена и вместимость совпали с v5;
ошибок исполнения и таймаутов не было. Для обычного режима медиана чтения архива —
480 мс, p95 — 1412 мс, максимум — 5311 мс. Замер исключает захват, декодирование PNG,
запуск OCR и игровую нагрузку; сравнивать его напрямую с другой выборкой нельзя.

## Запуск

Из каталога `app`:

```text
npm test
npm run simulate
npm run simulate:timers
node test/recognition-benchmark.js ../out/recognition-benchmark.json
node --test test/portal-recovery.test.js test/portal-recovery-pixels.test.js
```

Для симуляции и замеров требуется локальный каталог `calibration/`. Отчёты сохраняются в `out/`; оба каталога исключены из установщика.

Проверки `portal-recovery` используют собственные сохранённые fixtures и не требуют
`calibration/` или папок эксперимента. Они проверяют сохранение имени и вместимости,
обработку таймаута, ранний показ имени, BGRA, полный часовой разряд,
восстановление карточки и отказ от неподтверждённого времени. При проверке архивных
fixtures из модели исключаются шаблоны того же игрового эпизода.
